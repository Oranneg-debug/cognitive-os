## Article II: Specification Lifecycle

### Section 1. Proposal Creation (`/speckit.specify`)
When a spec-kit specification is created:

```
/specKit.specify <spec-title>
    ↓
ProposalWriter.create_proposal(origin='spec-kit')
    ↓
Draft proposal with:
  - origin: spec-kit
  - spec_reference: <spec-id>
  - status: draft
```

**Gates:**
1. Brand Guard reviews strategic alignment
2. Chairman assigns Board members to review

### Section 2. Planning (`/speckit.plan`)
When a specification enters the planning phase:

```
/speckit.plan
    ↓
Technical Meeting Council convened:
  - Architect creates technical blueprint
  - Creative expands with novel approaches  
  - Critic identifies failure modes
  - CTO synthesizes into final plan
```

**Output:** Technical Specification Document with implementation tasks

### Section 3. Task Generation (`/speckit.tasks`)
Tasks are generated by the HandoffPlanner:

```
/speckit.tasks
    ↓
HandoffPlanner parses technical spec
    ↓
Creates Alpha Handoff with:
  - tasks_total: N
  - tasks_completed: 0
  - implementation_tasks: [...]
```

### Section 4. Implementation (`/speckit.implement`)
Implementation follows the plan-code-review loop:

```
ALPHA STAGE
-----------
1. Technical Specialist implements feature
2. Beta Council reviews technical feasibility  
3. HandoffPlanner generates handoff document

BETA STAGE
----------
1. Alpha Polish Specialist refines UX/performance
2. Dev Final Audit gate verifies acceptance criteria
3. Final Scribe generates release notes
```

### Section 5. Analysis (`/speckit.analyze`)
Analysis uses `alpha_polish_check.py`:

```
/speckit.analyze
    ↓
Run alpha_polish_check.py against implementation
    ↓
Report gate results:
  - gate_count: X
  - gates_passed: Y
  - recommendations: [...]
```

## Article III: Anti-Patterns (Auto-Rejection Criteria)

The following anti-patterns trigger automatic rejection:

1. **BUG ACCOMMODATION** - Modifying tests to match buggy behavior
2. **ASSERTION INVERSION** - Changing assertions to match expected output
3. **SCOPE CREEP** - Adding tests beyond approved plan
4. **UNAUTHORIZED PROD EDITS** - Editing `src/` files without approval
5. **POLLUTION** - Disk writes without cleanup in `finally` block
6. **FALSE STATUS** - Claiming completion without passing all checks

## Article IV: Workflow Rules

### Section 1. Plan Stage
- Reviewer assigns one spec item (e.g., "D6")
- AI replies with plan (NO code)
- Reviewer approves or returns corrections

### Section 2. Act Stage  
- Write code and run pytest
- Paste FULL file contents in reply
- DO NOT commit - Reviewer commits

### Section 3. Review Stage
- Reviewer audits file and runs mutation tests
- Either accepts or rejects
- If rejected, fix per feedback
