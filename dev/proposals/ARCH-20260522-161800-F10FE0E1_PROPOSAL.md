## 📥 Original Request

> **Origin**: Systems Architect — supersedes earlier `DEV-20260521-WORKFLOW-EXECUTION` draft.

Build the state machine that drives proposals through their lifecycle, with a **hard approval gate** between planning and execution, and an immutable git-tag snapshot at the moment work begins.

---

## 🎯 Goal

After this lands:
- A single `WorkflowEngine` owns all phase transitions. `dev_route.py` and `kanban_processor.py` delegate; nobody else edits the `phase:` field.
- The planning → execution gate is **hard** — 5 checks, no override, blocked at the API level.
- Beta phase substatus (`planning` | `execution` with sub-states `coding`/`debugging`/`testing`/`ready-for-alpha`) lives in the proposal YAML, NOT in a new Kanban column. **Existing 6-column Kanban board stays as-is** — no user disruption.
- Every transition creates a handoff_vault snapshot, an approval_logger entry, and (at execution start) a git tag `exec-start/<proposal_id>` for guaranteed rollback.
- Bidirectional flow: rejection at any gate moves the card back to its prior column with a logged decision.

### G1-G6 Architectural Enhancements (binding)

| # | Enhancement | Why |
|---|-------------|-----|
| **G1** | **Per-proposal git branches** (`feat/proposal-{id}`) instead of v1.0's "global clean-tree" requirement | v1.0 required `git status --porcelain` to be empty globally before execution start. That BLOCKS parallel work on other proposals. G1: each proposal lives on its own branch; clean-tree check is per-branch. exec-start git tag still happens, just on the proposal branch. |
| **G2** | **Saga-pattern for transitions** with compensating actions: snapshot → git tag → YAML write → log; each step has a rollback compensation; on failure at step N, execute compensations 1..N-1 in reverse | v1.0 had ordered steps but no rollback contract. G2 makes atomicity explicit: a failed transition leaves the system at its pre-transition state, not in-between. |
| **G3** | **`version_hash`** (SHA-1 of current YAML frontmatter content) on every `TransitionRequest` | Prevents race condition: Obsidian-side edit + API-side transition attempt simultaneously. Server verifies `request.version_hash == current_yaml_hash`; returns **409 Conflict** on mismatch. Optimistic concurrency control. |
| **G4** | **Structured Gate #3 check via SQLite reads** (NOT freeform markdown parsing) | v1.0 said "grep `dev/decisions/{id}_log.md` for 3 APPROVED records". Fragile. G4: query `approval_log` table from Phase 1's SQLite index. SQL: `SELECT role FROM approval_log WHERE proposal_id=? AND decision='APPROVED' AND role IN ('analyst','architect','specialist') AND ts > now()-14d`. Needs all 3 distinct roles. |
| **G5** | **Creative direction** (from Creative role, brand-guard approved): dashboard substatus badges use gothic occult iconography; UI stark monochrome with blood-red highlights for gate failures; archive snapshots presented visually as "cursed relics" | Design/aesthetic direction for the Phase 3+4 dashboard UX. ## ✅ v1.2 — Technical Board Refinements (2026-05-23)

The ORCHESTRATED_TECHNICAL_OVERSEER council (task `task_20260523_132456_db8e7ecf`) confirmed v1.1 G1-G6 are architecturally sound and added 4 concrete operational refinements + 5 binding vetoes. All reviewer + brand-guard roles approved.

### T1-T4 Operational Refinements (binding)

| # | Refinement | Why it's needed (gap in v1.1) |
|---|------------|-------------------------------|
| **T1** | Git subprocess calls MUST have explicit timeouts AND run via `asyncio.to_thread` (or a structured async wrapper like GitPython) | v1.1's G1 specified per-proposal branches but didn't protect FastAPI workers from a hung `git tag`. Without timeout, one stuck git op blocks a worker indefinitely. |
| **T2** | `version_hash` (G3) must be computed ONLY from **semantic workflow keys**: `{phase, status, substatus, approver, severity, depends_on}`. Exclude volatile metadata like `last_modified`, `updated_ts`, etc. | v1.1's G3 used full-YAML SHA-1 — every `last_modified` tick (which happens on ANY file write, even from `proposal_sync`) would false-409 every concurrent transition request. T2 makes the hash stable across non-semantic edits. |
| **T3** | Saga compensating actions must be **explicit named functions per step**, not generic rollback logic | v1.1's G2 said "compensating actions" — vague. T3 forces concrete contract: each Saga step registers a named compensating function (e.g., `snapshot_step.compensate = lambda: mark_snapshot_superseded(hash)`). Generic try/except rollback is forbidden. |
| **T4** | Gate #3 SQLite query (G4) requires a **composite index** on `(proposal_id, role, decision, ts)` | v1.1's G4 specified the query shape but not the index. Without it: O(N) full scan on `approval_log` every Gate #3 evaluation. With composite index: O(log N). Matters once the log has thousands of rows. |

### T-V1 — T-V5 Affirmed Binding Vetoes

| # | Veto |
|---|------|
| **T-V1** | No raw subprocess git calls without timeouts (per T1) |
| **T-V2** | No hashing of volatile frontmatter fields for version control (per T2) |
| **T-V3** | No generic rollback logic; every Saga step must have a defined compensating function (per T3) |
| **T-V4** | No manual overrides of the hard planning→execution gate (reaffirmed from v1.1 V1) |
| **T-V5** | No direct writes to `phase:` field outside `WorkflowEngine` (reaffirmed from v1.1 V2) |

### Final implementation order (supersedes v1.1's order)

1. **`config/state_machine.yaml`** — phases + transitions + gate definitions (G4's structured SQLite query lives here as the Gate #3 spec; T4 adds the composite index migration SQL)
2. **`src/workflow_models.py` extensions** — `TransitionRequest` with `version_hash` field (T2: hash only semantic keys); `SagaTransaction` + `CompensatingAction` typed protocols (T3)
3. **`src/git_branch_manager.py`** — per-proposal branch lifecycle. **All git ops wrapped in `asyncio.to_thread` with explicit `timeout=` parameter** (T1). Use `subprocess.run(..., timeout=10)` minimum.
4. **`src/workflow_engine.py`** — `transition()` orchestrates the Saga. Each step has a `.compensate` attribute (T3). On any failure: run compensations 1..N-1 in reverse.
5. **SQLite migration**: add composite index on `approval_log(proposal_id, role, decision, ts)` before the first Gate #3 query (T4).
6. **Refactor `src/dev_route.py`** and **`src/kanban_processor.py`** — delegate to workflow_engine.
7. **API endpoints** — `POST /api/workflow/transition` accepts `TransitionRequest` with semantic-keys version_hash (T2); returns 409 Conflict on hash mismatch.
8. **Dashboard UI** — G5 creative direction (gothic substatus badges, blood-red gate-fail modal, snapshot history as "cursed relics").

| # | Check | Pass when |

## ⚠️ Difficulties & Constraints

1. **Technical**: `subprocess.run(["git", "tag", ...])` must be wrapped in `asyncio.to_thread` when called from FastAPI handlers.
2. **Technical**: The Kanban board file is a markdown file edited by Obsidian. If the user drags a card to `beta testing` from `proposal` while the gate would block planning→execution, that move is legal (it's column-level, not gate-level). The gate fires only at the planning→execution sub-state transition. Document this clearly in the user docs.
3. **Technical**: Git tag creation requires a clean working tree. The gate check explicitly fails if uncommitted changes exist — the user must commit or stash before starting execution.
4. **Operational**: First boot after this lands must auto-set `substatus: planning` for every existing proposal currently in `beta_testing` (legacy migration). Idempotent.
5. **Aesthetic / Sovereign**: No automatic phase advancement. Every transition is user-initiated (dashboard button or Kanban drag).
