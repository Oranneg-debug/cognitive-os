# **Structured State Management for Proposal Workflows**
*A Technical Blueprint for Efficient, Robust, and Scalable Phase Transition*

---

## **1. Executive Summary**
The current proposal pipeline suffers from inefficient state management: each phase reprocesses raw markdown content, leading to redundant parsing overhead, increased token costs, and potential AI hallucinations. This report outlines a **hybrid architecture** combining **YAML frontmatter** (for compact metadata) and **JSON cache files** (for large structured outputs), ensuring deterministic transitions between phases while mitigating risks like unbounded growth or validation failures.

---

## **2. Core Problem & Opportunity**
### **Current State**
- Phases (`beta_council`, `alpha_polish`) must parse entire markdown files, wasting computational resources.
- No standardized way to pass structured intermediate results between steps.

### **Opportunity**
Replace raw markdown with:
1. **YAML Frontmatter** (≤5KB) for lightweight metadata/configuration.
2. **JSON Cache Files** for large artifacts referenced via hashes in frontmatter.

**Benefits**:
- Faster, more reliable state transitions.
- Reduced token costs and parsing errors.
- Scalable separation of small metadata vs. complex outputs.

---

## **3. Deliberation History & Key Decisions**

### **[2026-05-19] Technical Specialist (qwen3.6)**
**Proposal**:
- Define a versioned, append-only schema for frontmatter.
- Enforce typed structures (`string`, `bool`, `object`) to prevent parsing drift.
- Implement idempotent patching: phases update **only their subtree**.
- Limit frontmatter size (≤5KB) via external cache files for large outputs.

**Actionable Steps**:
1. Draft a YAML schema with:
   ```yaml
   metadata:
     id: "proposal_X"
     version: 2
     updated_at: "2026-05-20T12:00:00Z"
   config:
     roles: ["beta_council", "alpha_polish"]
     constraints: { max_frontmatter_size: 5000 }
   phases:
     beta_council:
       output: {}
       status: pending
   ```
2. Validate against `beta_council` output to ensure parse stability.

---

### **[2026-05-19] Technical Creative (hermes-4.3)**
**Complementary Suggestion**:
- **Phase Cache Files**: Temporary JSON files (`proposal_X_hash.state.json`) for large outputs.
  - *Use Case*: Beta Council generates detailed structured data; cache it externally, referencing the file in frontmatter.

**Rationale**:
- Keeps frontmatter compact while preserving critical artifacts.
- Avoids re-parsing raw markdown for phases needing granular details.

---

### **[2026-05-19] Technical Critic (deepseek-r1-distill)**
**Critical Risks & Mitigations**:
| **Risk**                          | **Mitigation**                                                                 |
|-----------------------------------|--------------------------------------------------------------------------------|
| Unbounded frontmatter growth       | Schema limits to 5KB; cache large outputs externally.                           |
| Validation failures                | Pre-write JSON Schema + post-read linting.                                    |
| Cache file synchronization         | Frontmatter references must exist on disk (idempotent checks).               |
| Backward compatibility             | Versioned `metadata.version` for future schema updates.                       |

**Veto Points**:
- No unstructured blobs in frontmatter.
- Phases **never overwrite global metadata**.
- Cache files referenced in frontmatter must exist.

---

## **4. Definitive Blueprint**
### **Architecture**
1. **Frontmatter (YAML)**:
   - Size: ≤5KB; contains metadata, config, and phase summaries.
   - Example:
     ```yaml
     ---
     metadata:
       id: "proposal_2026"
       version: 3
       updated_at: "2026-05-21T09:45:00Z"
     phases:
       beta_council:
         output_hash: "sha256:abc123"
         status: completed
     ```

2. **Cache Files (JSON)**:
   - Stores large outputs (e.g., `beta_council_output.json`).
   - Referenced via hash in frontmatter.

### **Schema Enforcement**
- Canonical keys enforced:
  ```yaml
  metadata.version       # Incremented on every write.
  phases.<role>.output   # Structured outputs (typed: string/bool/object/array).
  ```
- Schema validation via JSON Schema before commits.

### **Patch Strategy**
1. Read existing frontmatter.
2. Patch only the target phase’s subtree:
   ```yaml
   # Before:
   phases:
     beta_council: { output: raw_data }
     alpha_polish: { status: pending }

   # After (idempotent patch):
   phases:
     beta_council: { output_hash: "sha256:xyz456", status: completed }
     alpha_polish: { status: pending }  # Unchanged!
   ```
3. Write back validated YAML.

### **Validation Layer**
- Pre-write JSON Schema validation (e.g., for `phases.<role>.output`).
- Post-read linting to catch malformed YAML before next prompt.

---

## **5. Risks & Guardrails**
| **Risk**                          | **Mitigation**                                                                 |
|-----------------------------------|--------------------------------------------------------------------------------|
| Cache file references broken       | Frontmatter validation ensures cache files exist on disk.                      |
| Schema drift across phases         | Versioned `metadata.version` enables backward-compatible updates.             |
| Token cost spikes                 | Frontmatter capped at 5KB; large outputs cached externally.                   |

**Veto Points**:
- No unstructured JSON blobs in frontmatter.
- Phases **must not overwrite global metadata**.
- Cache files referenced in frontmatter must exist.

---

4. **Deploy Validation Layer**: Pre-write JSON Schema + post-read linting.
