## 📥 Original Request

> **Origin**: Direct (post-mortem of failed n_parallel / KV-quant / context_window load attempts on hermes-4.3-36b)

Migrate the Cognitive OS LM Studio integration from the **non-existent `POST /api/v1/models/load` REST endpoint** to the **official `lmstudio` Python SDK** (which uses LM Studio's real WebSocket/RPC channel). Surface the full set of load controls (context, parallel slots, KV quant, FA, GPU offload, tensor split) per-model in `master_config.md` *and* as live controls in the dashboard's Configuration tab — so every load setting is a first-class, code-controlled, version-tracked parameter rather than a hidden GUI preference that drifts across sessions.

---

## 🔍 Problem Statement

### What we discovered

`cognitive-os/src/llm_client.py` has been POSTing load configurations to `http://localhost:1234/api/v1/models/load` for every JIT load since the project began. **That endpoint does not exist in LM Studio's REST surface.** Evidence:

- LM Studio's OpenAPI-compatible REST surface is limited to `/v1/chat/completions`, `/v1/models`, `/v1/embeddings`. Confirmed against `lmstudio-ai/lmstudio-js` and `lmstudio-ai/lmstudio-python` source trees.
- All load operations in those repos go through the proprietary `lms-shared-types` WebSocket channel via `llm.load_new_instance(...)` / `_get_or_load(...)`.
- The `lms` CLI uses the same channel; the `--parallel` flag maps to `maxParallelPredictions`.

### Observable symptom

A live `LlamaV4::load` debug log from 2026-05-21 00:00 shows the load config arriving as `n_parallel=4 n_ctx=131072` despite our payload specifying `maxParallelPredictions=1` and `context_window` from `master_config.md`. The four KV slots cost ~17 GiB at q8_0 → `cudaMalloc failed: out of memory` → `retrying without pipeline parallelism` → 5.6 tok/s on dual 3090s (should be 25–40 tok/s).

### Silent side effects (last ~3 months)

Every "fix" that touched `gpu_offload_ratio`, `flash_attention`, `cache_type_k`, `cache_type_v`, `context_window`, or `gpu_layers` has been a **placebo**. LM Studio's JIT auto-load (triggered by the chat-completions call that follows) ignores our POST and uses the per-model preferences stored in its GUI config — which is also why **eject + reload** sometimes "fixed" things (the GUI prefs had been re-saved between attempts).

---

## 🎯 Goal

Full programmatic control of LM Studio load configuration from the Cognitive OS stack, with:

1. **Code as source of truth.** Every load parameter declared in `master_config.md` actually reaches the runtime.
2. **Dashboard transparency.** Every load parameter is visible and editable in the Configuration tab; pushing "Save" reloads the model with the new settings.
3. **No hidden GUI-pref drift.** A clean checkout reproduces the exact same loaded-model behaviour every time.
4. **No regressions.** Existing OpenAI-client inference path keeps working; only the load layer changes.

### Known LM Studio behaviour discovered during bootstrap

The bootstrap process empirically confirmed that **LM Studio caps `n_ctx` to 8192 (or lower, with progressive decay) on CPU-pinned models**, regardless of `master_config.md` value, CLI `-c` flag, or saved per-model GUI default. This is LM Studio runtime behaviour, NOT a code defect.

Consequence: roles that receive long inputs (notably `scribe`, which gets the full council transcript) MUST run on GPU. The follow-up proposal `ARCH-...-VRAM-POLICY` (to be filed post-bootstrap) will codify the GPU/CPU role placement policy and document this constraint.

## 🛠 Proposed Approach

Two-channel architecture. Keep the OpenAI client for **inference** (already battle-tested, async-friendly, OpenAI-API compatible for tooling), introduce the `lmstudio` Python SDK for **lifecycle** (load, unload, list, configure).

```
┌────────────────────────────────────────────┐
│             Orchestrator                   │
└────────────────────┬───────────────────────┘
                     │
        ┌────────────┴────────────┐
        │                         │
        ▼                         ▼
┌──────────────────┐    ┌──────────────────────┐
│  LMStudioLoader  │    │   InferenceClient    │
│  (new)           │    │   (existing OpenAI)  │
│                  │    │                      │
│  • load_model    │    │  • chat.completions  │
│  • unload_model  │    │  • streaming         │
│  • list_loaded   │    │  • image_base64      │
│  • get_config    │    │                      │
│  uses: lmstudio  │    │  uses: openai client │
│         python   │    │         /v1/chat/... │
└──────────────────┘    └──────────────────────┘
```

### Migration shape

1. Add `lmstudio` to `requirements.txt` (pin version once we validate).
2. Create `src/lmstudio_loader.py` with the four lifecycle methods above. Sync API to match existing call sites.
3. Refactor `llm_client.py::generate_response` so the "explicit load" block delegates to `LMStudioLoader.ensure_loaded(model, config)` instead of the broken POST.
4. Extend `master_config.md` model entries with the full schema (context, parallel, KV, FA, GPU, tensor split). Validate on load.
5. Add `GET /api/loaded` and `POST /api/load` endpoints to `src/api.py` — both backed by `LMStudioLoader`.
6. Add a "Load Settings" panel to the dashboard's per-model configuration view; pushing Save triggers reload via `POST /api/load`.

### Why not the `lms` CLI?

- Subprocess overhead per call.
- No structured error returns — have to scrape stdout.
- Can't subscribe to load-progress events for dashboard feedback.
- Still requires the SDK to be installed for the CLI itself.

### Why not raw WebSocket?

- Reimplementing the lms-shared-types protocol means re-inventing the SDK.
- Maintenance burden every time LM Studio bumps protocol version.
- The Python SDK is open-source, MIT, maintained by LM Studio.

## ⚠️ Difficulties & Constraints

### Technical risks

1. **Sync vs async impedance.** `lmstudio-python` has both sync and async clients. Orchestrator is currently sync; FastAPI endpoints are async. Need a clean adapter or pick one mode. *Recommended: sync client for now (matches orchestrator), revisit when we move to streaming.*
2. **`is_loaded` race.** Our current `loaded_models.list()` check has a 200-300 ms race with LM Studio's auto-eject TTL. The SDK exposes a proper `get_or_load` primitive — use it.
3. **GUI-pref drift on first run.** Existing models already have settings cached in LM Studio's per-model JSON. First SDK load with our config overwrites them — irreversible on user's machine. *Mitigation: snapshot LM Studio's `~/.lmstudio/.internal/per-model-configs/` to a backup folder before first run, log it.*
4. **Eject + reload latency.** Changing context length requires a full reload (~15 s for hermes Q6). Don't let dashboard "Save" silently freeze the UI — fire-and-forget with progress events.
5. **SDK version stability.** `lmstudio-python` is < 1.0 at time of writing. Pin to a tested version; document upgrade path.
6. **Tensor split exposure.** The SDK supports it via the `gpu` block (`split: [0.5, 0.5]`). Worth adding to surface dual-GPU users without UI gymnastics.

### Operational risks

7. **Existing model state on dev machine.** User's LM Studio has cached prefs (e.g. hermes KV currently `q8_0` from earlier fiddling). First SDK load needs to take precedence cleanly — verify before we ship.
8. **Long-running orchestrator process.** SDK session may need keep-alive; ensure we don't leak handles between turns.

### Creative / aesthetic constraints

9. **Dashboard load-settings panel must respect the Dark Maestro design language.** No third-party widget libraries; reuse existing form patterns. The panel is *operational*, not a UX showcase — it should feel like an instrument readout, not a wizard.

### Audit Report (Overseer)

> Synthesis reveals three critical implementation gaps:
>
> 1. **SDK volatility** requires an abstraction layer (`ILmStudioLifecycle`) to isolate breaking changes.
> 2. **Sync SDK calls in FastAPI** must be offloaded via `asyncio.to_thread` or executor to prevent event-loop blocking during heavy load/unload cycles.
> 3. **Dashboard UI** must strictly enforce *Analog Readout* aesthetics (monospaced, high-contrast) rather than generic form libraries.
>
> The proposed two-channel architecture is verified as **the only viable path forward**.

### Definitive Blueprint (Overseer)

1. **Core interface** — Define `ILmStudioLifecycle` abstract base class for SDK-agnostic lifecycle management.
2. **Config schema** — Enforce **Pydantic validation** on all load parameters (context, parallel, KV, FA) before transmission to runtime.
3. **Async wrapper** — Implement `LMStudioLoader` using `asyncio.to_thread` for sync SDK calls to preserve FastAPI responsiveness; expose SSE/WebSocket for progress streaming.
4. **API layer** — Add `GET /api/loaded` + `POST /api/load` endpoints backed by the loader; validate config on entry.
5. **Dashboard UI** — Build the "Load Settings" panel with custom CSS (Iosevka Mono, high contrast) to mimic an instrument readout; disable inputs during reload state.
6. **State management** — Snapshot LM Studio GUI prefs prior to first SDK run to prevent irreversible drift.

### Vetoes (Overseer)

| Type | Reason |
|---|---|
| Architecture | Blocking FastAPI event loop with sync SDK calls without executor isolation. |
| Data Integrity | Allowing unvalidated or partial load configs to reach LM Studio runtime (silent drift). |
| Performance | Using fixed token/sec thresholds as universal pass/fail gates across hardware variances. *(Note: the boardroom later accepted ≥25 tok/s as scoped to **this machine's dual-3090 baseline**, not a universal floor.)* |
| Aesthetic | Introducing Material Design widgets or gradients that violate the Dark Maestro "Analog Readout" mandate. |

### Reconciliation (Boardroom ↔ Technical)

The two councils agreed on the **substance** of the migration. Notable deltas:

- **Abstract base class (`ILmStudioLifecycle`)** — proposed by Technical Overseer, *not* adopted in the boardroom action plan. Likely deemed over-engineered for an SDK we'll be pinned to. Open question: revisit if SDK proves unstable.
- **Pydantic validation** — promoted by Technical Overseer as a first-class step. Boardroom folded this into task #4 ("strict schema validation") but didn't mandate Pydantic specifically. Implementation choice.
- **Performance gate** — Technical Overseer vetoed fixed tps thresholds as "hardware-agnostic". Boardroom kept ≥25 tok/s but scoped it to "dual-GPU environment" in quality gate #1. Acceptable resolution.
- **Implementation order** — Boardroom enforced a deadline tree (May 28 → June 14). Technical Overseer enumerated steps but didn't sequence them. Boardroom timing wins.
