## 📥 Original Request

> **Origin**: User question during Phase 3+4 review — "isn't it a good idea to move the whole kanban to the dashboard and away from obsidian… keep the developer side completely separated from the using side?"

Move the **Kanban state and editing surface** out of the Obsidian vault into the dashboard. Obsidian keeps the **content** (proposal markdown, AI Output notes, design requests, user thinking-space). The vault stops being a database; it becomes a thinking space again.

---

## 🎯 Goal

After this lands:
- **State store**: `cognitive-os/dev/kanban_state.sqlite` is the single source of truth for which card is in which column, what its substatus is, what its history is.
- **Editor**: Dashboard Kanban tab is the only place a card can be moved. Drag-drop → `POST /api/workflow/transition` → state machine → SQLite + handoff_vault snapshot.
- **Vault mirror**: `Dev-KanBan.md` is **regenerated** by the API after every state change. Vault users can read it (mobile, offline, glanceable) but edits are not read back. No more parse loop, no more drag-watcher race.
- **Cleaner separation**: 
  - **Developer side**: dashboard + API + SQLite (gates, transitions, substatus, history)
  - **User side**: vault (proposal content, AI outputs, design notes — no process state)
- **Existing 4 ARCH proposals continue to fit**:
  - Phase 0 refactor → unchanged
  - Phase 1 governance → unchanged
  - Phase 2 routing → small amendment (apply() writes to kanban_state, not markdown)
  - Phase 3+4 workflow → state machine writes to kanban_state instead of editing markdown

### Approval workflow (post-this-proposal)

```
1. Dashboard Kanban tab lists ARCH-/DEV-/NLST- cards in their columns.
2. User clicks a card → side panel opens with proposal body + history.
3. Side panel has [Run Boardroom] / [Run Technical Board] / [Run Architect] buttons.
4. Clicking a button POSTs to /process with the appropriate council marker
   (#boardroom / #technical / #architect) and the proposal body as input.
5. Streaming synthesis renders inline.
6. When the council finishes, three buttons appear: APPROVE / REJECT / CONDITIONAL.
7. Click APPROVE → POST /api/workflow/transition with:
       proposal_id, target_column='beta testing', target_substatus='planning',
       approver=<user>, reason=<paste of synthesis summary>
   → workflow_engine validates gate (if any) → writes kanban_store + handoff_vault
   → renderer regenerates Dev-KanBan.md
8. Click REJECT → target_column='backlog', logged in transitions table.
9. Click CONDITIONAL → stays in 'proposal' column, conditions appended to
   proposal body, ApprovalRecord written with decision='conditional'.
```

No file edit. No YAML regex. No vault touch. One click per decision.

### Schema

```sql
CREATE TABLE cards (
    proposal_id    TEXT PRIMARY KEY,        -- DEV-… / ARCH-… / NLST-…
    prefix         TEXT NOT NULL,           -- 'DEV' | 'ARCH' | 'NLST'
    title          TEXT,
    column_name    TEXT NOT NULL,           -- 'backlog' | 'proposal' | …
    substatus      TEXT,                    -- nullable; for beta_testing: 'planning' | 'execution.coding' | …
    severity       TEXT,                    -- 'high' | 'medium' | 'low' | 'unknown'
    origin         TEXT,
    created_ts     TEXT NOT NULL,           -- ISO 8601
    updated_ts     TEXT NOT NULL,
    state_hash     TEXT                     -- SHA256 of (column,substatus) — quick diff for renderer
);

CREATE TABLE transitions (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    proposal_id    TEXT NOT NULL,
    from_column    TEXT,                    -- NULL for initial insert
    to_column      TEXT NOT NULL,
    from_substatus TEXT,
    to_substatus   TEXT,
    approver       TEXT NOT NULL,
    reason         TEXT,
    gate_passed    INTEGER,                 -- 0=N/A, 1=passed, -1=failed
    gate_details   TEXT,                    -- JSON: {failed: [...], passed: [...]}
    archive_hash   TEXT,                    -- links to handoff_vault snapshot
    ts             TEXT NOT NULL,
    FOREIGN KEY (proposal_id) REFERENCES cards(proposal_id)
);

CREATE INDEX idx_transitions_proposal ON transitions(proposal_id, ts);
CREATE INDEX idx_cards_column ON cards(column_name, updated_ts DESC);
```

### One-time migration

| Step | Action |
|---|---|
| 1 | Parse current `Dev-KanBan.md` ONE LAST TIME using existing `kanban_processor._parse_kanban_board` |
| 2 | For every detected card, INSERT INTO `cards` with current column |
| 3 | Cross-reference `dev/proposals/*.md` frontmatter (`phase`, `status`, `severity`, `origin`, `prefix`) to fill the rest |
| 4 | Cards in vault but not on disk → INSERT with `column='backlog'`, log warning |
| 5 | Proposals on disk but not on board → INSERT with `column='backlog'` (covers backfill of the 4 ARCH proposals + the supersedes for old DEV-20260521-* drafts) |

| 7 | Delete `dev/.kanban_cache.json` |
| 8 | Migration writes a report to `dev/decisions/_kanban_migration_2026-05-XX.md` (uses Phase 1 approval_logger if available, else stderr) |

Migration is **idempotent**: re-running it does nothing if SQLite is already populated.

## ⚠️ Difficulties & Constraints

1. **Technical**: SQLite writes from async FastAPI routes — every store call wrapped in `asyncio.to_thread`. Foreign-key enforcement enabled (`PRAGMA foreign_keys=ON`).
2. **Technical**: Backup discipline. Before every migration / schema change, `kanban_store.backup()` runs `VACUUM INTO 'dev/.backups/kanban_state_<ts>.sqlite'`. Keep last 10.
3. **Technical**: Dashboard drag-drop is native HTML5 drag events; no React, no extra framework — stays consistent with existing dashboard (vanilla JS).
4. **Operational**: Mobile users still want a Kanban view. The vault mirror solves this — it's still browsable in Obsidian Mobile, just not *editable* (any edit to `Dev-KanBan.md` is overwritten on the next state change). Add a header comment in the rendered markdown: `<!-- AUTO-GENERATED by kanban_renderer.py at <ts>. Edits will be overwritten. Drag cards in the dashboard. -->`
5. **Operational**: The dashboard is the only editor — if the API is down, the user can't move cards. Acceptable trade-off because the API is also needed for gate checks, transitions, archives. If the API is down, nothing about the dev process works anyway.
6. **Aesthetic / Sovereign**: Vault becomes thinking-space again. No more emoji status soup in the seedlings folder. Process state lives where process logic lives.
7. **Migration risk**: ONE-WAY. Once a card is in SQLite, vault edits are lost. Pre-migration backup of `Dev-KanBan.md` is mandatory (handled by step 1's parse + the existing `.bak.<ts>` mechanism in sync_proposals_to_kanban).

## 🚫 Veto Points

- ❌ **Two writers on `Dev-KanBan.md`.** Only `kanban_renderer.write_vault_mirror()` touches it. Anyone else (sync, processor, dev_route) is forbidden.
- ❌ **Reading the markdown back after migration.** Vault mirror is write-only from the system's perspective.
- ❌ **A second cache file.** SQLite replaces `.kanban_cache.json`; do not introduce `.kanban_state.json` or similar in parallel.
- ❌ **Storing process state (status emojis, phase numbers) anywhere in the vault besides the auto-generated mirror.** Vault returns to being a thinking space.
- ❌ **Web framework creep.** No React / Vue / Svelte for the Kanban UI — vanilla JS + native HTML5 drag events. Keeps the dashboard one cohesive surface.
- ❌ **Letting `workflow_engine` write to markdown.** It writes to `kanban_store`; the renderer regenerates the markdown as a side-effect.
- ❌ **Skipping the gate-fail modal.** Gates only matter if the UI surfaces them. A silent 422 is a regression.
- ❌ **Approval via vault edits.** Manually editing the YAML status / phase in a proposal markdown does NOT advance the workflow. The dashboard is the only authority. (Schema validator from Phase 1 will detect tampering and log it, but the kanban_store remains the source of truth.)
- ❌ **Dev-process triggers from Obsidian** (`/dev`, `/technical`, `/boardroom`, `/architect`, `/analyst`). Removed in this proposal. User-side triggers (`/oracle`, `/design`, `/nft`) are preserved.
- ❌ **Hashtag-fired councils.** `#boardroom` / `#dev` / `#technical` inside a vault note are passive metadata — they no longer trigger a council on save. (The `output_router` from Phase 2 still parses these tags inside *council outputs*, not user notes.)
- ❌ **Approval automation.** No "auto-approve if quorum reached" rules. Every transition is a deliberate human click.
