## 📥 Original Request

> **Origin**: Systems Architect — captured from user request:
> *"We need to have a complete handoff ready for qwen3-coder-next after that board, no more in-between steps. Beta council or a planner needs to produce a complete plan, ready for Qwen3-Coder-Next or Deepseek-Coder-V2-Lite."*

The current pipeline:

```
council verdict  →  handoff_writer extracts "Implementation Tasks" via regex grep
                 →  if regex misses (fenced code, nested structure, prose-only): placeholder
                 →  human manually prepends a checklist (observed twice: Phase 5, DevLog Agent)
                 →  editor finally has a plan to work from
```

Observed failure mode: tech-board outputs its plan inside a `\`\`\`markdown` fenced block. The
extractor's regex doesn't descend into fences. Falls through to `"- [ ] See full council report
for tasks"`. Cline reads the handoff, sees one placeholder line, has to read the entire
deliberation report to reconstruct tasks — which is exactly what we built the council to do for him.

This proposal inserts a deterministic planner step between verdict and handoff.

---

## 🎯 Goal

After this lands:

- Every Beta and Alpha handoff has a **complete, tickable, Cline-ready** `## 🔧 Implementation Tasks` section, populated automatically
- The receiving editor (Qwen3-Coder-Next, Deepseek-Coder-V2-Lite, future models) can flip Plan-mode → Act-mode without human cleanup
- Tasks include explicit acceptance criteria, file paths, binding-constraint references, and dependency markers
- The boardroom/tech-board councils stay focused on **deliberation** (their strength); the planner stays focused on **decomposition into editor-shaped work** (a different skill)
- Zero manual handoff prep from the human side

## 🔍 Current Shape (problem statement)

### What `handoff_writer.generate_beta_handoff` does today

```python
tasks_raw = _extract_section(council_report, "Implementation Tasks", "Tasks", ...)
if tasks_raw:
    task_lines = []
    for line in tasks_raw.splitlines():
        # normalise bullet/number to checkbox
        ...
    tasks_block = "\n".join(task_lines)
else:
    tasks_block = "- [ ] See full council report below for implementation guidance"
```

**Failure modes:**

1. **Fenced code blocks.** If the council emits `\`\`\`markdown\n## Tasks\n...\n\`\`\``, the
   regex doesn't see "## Tasks" because it's inside a fence. Falls to placeholder.
2. **Prose-only verdict.** Some council outputs are pure deliberation without a structured
   task section. No "Implementation Tasks" header → placeholder.
3. **Nested under deliberation.** When the council buries tasks under `## Final Verdict →
   ### Action Items → bullet list`, the extractor matches `Action Items` but misses
   surrounding context that's load-bearing for the task.
4. **No acceptance criteria per task.** Even when extraction works, each line is just
   "do X" — no "X is done when Y passes", no path, no test reference.

### What we want instead

Each handoff task line should encode enough context that an editor can pick it up cold:

```markdown
- [ ] **A1. `src/api.py` → OutputRouter**
   - [ ] Boot-time: instantiate `OutputRouter(rules_path=paths.CONFIG_DIR/"routing_rules.yaml", ...)`
   - [ ] Replace inline string-matching in `/process` with `router.route(synthesis)` → `router.apply(...)`
   - [ ] Acceptance: `tests/integration/test_api_process_uses_output_router.py` passes
   - [ ] Constraint: H3 (direct injection — NOT via orchestrator delegation)
```

The planner's job is to take the raw council verdict + the proposal + the binding constraints
and emit a checklist of this shape.

## ✅ Deliverables

### Section A — The HandoffPlanner role

1. **New role in `dev/master_config.md`** under `roles:`:
   ```yaml
   handoff_planner:
     model: ministral-3-3b-instruct-2512    # fast; planner doesn't need genius, it needs structure
     compass_weight: IGNORE
     context_window: 131072                  # must fit proposal + verdict + binding constraints
     temperature: 0.3                        # determinism > creativity
     top_p: 0.9
     top_k: 40
     min_p: 0.1
     max_tokens: 8192                        # enough for ~30-50 detailed checklist items
     gpu_layers: -1
     n_parallel: 1
     system_prompt: |
       You are the Handoff Planner. Your job is to decompose a council verdict
       into a code-ready implementation checklist for an editor agent.
       Output ONLY valid markdown with the EXACT structure described below.
       Do NOT add prose commentary, do NOT wrap output in code fences.
       Every task must be a single ticked-checkbox line. Group by logical section.
       Each task line includes: file path, exact change, acceptance criterion,
       binding constraint reference (e.g. "H3" or "CSTR-X-V2").
   ```

2. **New module: `src/handoff_planner.py`**
   - Class `HandoffPlanner` with:
     - `plan(proposal: ValidatedProposal, council_report: str, binding_constraints: list[str]) -> HandoffPlan`
     - `HandoffPlan` Pydantic model: `sections: list[PlanSection]`, each with `name`, `tasks: list[PlanTask]`
     - `PlanTask` Pydantic model: `id` (e.g. "A1"), `title`, `subtasks: list[str]`, `acceptance: str`, `constraints: list[str]`, `file_paths: list[Path]`
   - Internally:
     - Strips fences from `council_report` via `src.markdown_fence_parser.strip_fences`
     - Calls the `handoff_planner` LLM role with a strict prompt
     - Validates the LLM output against the Pydantic schema (E3-style fail-fast)
     - On validation failure: retries once with the validator error embedded in the prompt
     - On second failure: returns a `HandoffPlan` with a single placeholder task pointing at the dead-letter

3. **`HandoffPlan.to_markdown()` method**
   - Renders the structured plan into the `## 🔧 Implementation Tasks` section format
   - Stable across runs (same plan → same markdown)

### Section B — Wire the planner into the existing handoff pipeline

4. **`src/handoff_writer.generate_beta_handoff` modified** to:
   - Call `HandoffPlanner().plan(...)` instead of regex-extracting tasks
   - On planner failure (network, model unavailable, validation): fall back to the OLD extractor with a clear "PLANNER FAILED, FALLBACK ACTIVE" notice at the top of the tasks section
   - The fallback ensures no degradation — if the planner is broken, behaviour matches today

5. **`src/handoff_writer.generate_alpha_handoff` modified the same way**

6. **`src/orchestrator.execute_technical_meeting`** and **`execute_sequential_boardroom`**:
   - Currently return `report` (string). Change to return `{"report": str, "plan": HandoffPlan}` so the planner runs in the same orchestration context
   - Backward-compatible: callers that only use `["report"]` keep working

### Section C — Strict output format spec

7. **`docs/HANDOFF_PLANNER_OUTPUT_SPEC.md`** documents the exact markdown shape:
   - Section headers `### Section A — ...`
   - Numbered top-level tasks `- [ ] **A1. <title>**`
   - Indented sub-tasks `   - [ ] <step>`
   - Acceptance line per top-level task `   - **Acceptance**: <criterion>`
   - Constraint reference per task `   - **Constraints**: H3, CSTR-X-V2`
   - File-path reference per task `   - **Files**: src/api.py, tests/integration/test_x.py`
   - This is the spec the LLM is prompted against AND the Pydantic schema validates against

## 🛡 Binding constraints (anticipated)

**CSTR-PLANNER-V1 — No new dependencies.** Use stdlib + already-installed (Pydantic, ruamel.yaml). No `langchain`, no `pydantic-ai`, no template engines. The planner is one LLM call + validation, that's all.

**CSTR-PLANNER-V2 — Planner failure NEVER blocks the handoff.** If the planner times out, errors, or emits invalid JSON twice, the handoff falls back to today's extractor with a visible notice. Zero data loss; user can re-run the planner manually.

**CSTR-PLANNER-V3 — Strip fences before the planner sees text.** Use `src.markdown_fence_parser.strip_fences()` — already in production from Phase 2. Don't reinvent.

**CSTR-PLANNER-V4 — Planner output is Pydantic-validated.** Match the Phase 1 / Phase 2 pattern: schema-first, fail-fast.

**CSTR-PLANNER-V5 — Idempotent.** Running the planner twice on the same verdict produces equivalent (not necessarily byte-identical) plans. Tests assert structural equivalence.

**CSTR-PLANNER-V6 — Planner has no knowledge of editor identity.** The output format is editor-agnostic. Qwen3-Coder-Next reads the same handoff as Deepseek-Coder-V2-Lite, as a future Claude editor, as a human in VS Code. No `if model == "qwen3"` branching anywhere.

## 🧠 Technical Assessment

### Complexity
**Low-medium.** One new module (~250 LOC), one role config, two small wiring changes in `handoff_writer.py`, ~600 LOC of tests. The hard part is the **system prompt** — needs to produce structured output reliably from a 3B model at temp 0.3.

### Why ministral-3-3b for the planner
- Already loaded as moderator/scribe — no new model to download or VRAM to allocate
- Fast (the planner runs synchronously inside the council orchestration)
- Determinism over creativity — a 3B at temp 0.3 with a tight schema is what you want
- If it underperforms: trivial to swap to `qwen3-vl-4b-thinking` (also already loaded) via master_config

### Why NOT have the council emit structured tasks directly
Considered + rejected:
- Asking 11 council roles to coordinate on a strict output format = guaranteed drift
- Roles disagree about what "task" means (Strategist sees milestones, Specialist sees commits, Critic sees risks-to-mitigate)
- The chairman synthesis already merges those views into prose; a dedicated planner is the right
  abstraction layer
- This is the same logic as Phase 2's "router after council, not router-as-role"

### Risk
- **3B model emitting structured markdown reliably.** Mitigation: strict system prompt + Pydantic validation + one retry with validator-error injected. If the 3B can't hold the shape, swap to 4B.
- **Planner becomes a chokepoint.** A council taking 10 min + a planner taking 30s is fine. A planner taking 5 min is not. Time-box the planner to 60s; on timeout → fallback.
- **Plan drift between proposal version and planner output.** When proposal is amended (e.g. v1.0 → v1.1 boardroom amendments), the planner must read the LATEST version. Already handled by reading the proposal file at planner-call time, but explicit.

## 🎨 Aesthetic direction

Generated tasks adopt Dark Maestro style:
- Task lines use `- [ ]` (not `- [x]` until done; planner emits unticked)
- Section headers `### Section A — Title` (em-dash, no decoration)
- Path references in backticks
- Constraint references in ALL CAPS short form (H3, V2, CSTR-…)
- No filler ("As you can see", "It is important to note", etc.)
- No emoji in task bodies (✅/❌ only allowed in acceptance criteria)

## Notes for Beta Council

When reviewing, please specifically address:

1. **Is ministral-3-3b the right model for the planner role?** Or should we default to qwen3-vl-4b-thinking (already loaded as vision/brand_guard) for the slightly better structural-output reliability?

2. **Should the planner emit YAML instead of markdown** for the structured task list, then have a separate render step? Easier validation, but adds a transform layer. Lean toward markdown-with-Pydantic-parsing for fewer moving parts.

3. **Should the planner have access to `src/` source code** to reference specific function names in task descriptions? Or does it work purely from the proposal + verdict text? Source access = richer plans but introduces a context-budget concern.

4. **Should we add a separate `replan` CLI command** so any handoff can be re-planned later if the editor reports the original was unclear? `scripts/devlog.py replan ARCH-XXX` style.

5. **Failure mode for malformed council verdict:** if the verdict itself is broken (e.g. truncated mid-stream), should the planner refuse to plan? Or always emit something so the handoff exists? Lean toward "emit a single-task plan that says 'verdict appears truncated, manual review required' and dead-letter the input."
