## 📥 Original Request

> **Origin**: Systems Architect agent — triggered by user observation that model settings in the Obsidian plugin feel "too embedded in the system" and a follow-up question about dropping the 3rd-party AI Providers SDK.

Refactor the `obsidian-lmstudio-agent` Obsidian plugin to be a clean, modular input adapter with a single source of truth for model configuration (the backend's `master_config.md`). Consolidate duplicated HTTP logic, split the ~2100-line `chat-view.ts` monolith into per-tool modules, extract Cognitive OS menu wiring from `main.ts`, and formalise the model-preset contract across the plugin↔backend boundary.

---

## 🎯 Goal

The `obsidian-lmstudio-agent` plugin currently carries three layers of redundancy that make it fragile to change: (1) model presets are duplicated verbatim in both `settings.ts` and `master_config.md`, (2) 7 per-tool model-picker slots in `AgentPluginSettings` are a parallel configuration system the backend never reads, and (3) the Cognitive OS HTTP POST is implemented twice — once cleanly in `cogOsService.ts` and once duplicated inline in `canvas-commands.ts`. Additionally, `chat-view.ts` is a ~2100-line monolith doing chat rendering, tool execution, model resolution, RAG search, permissions, history, undo, and Cognitive OS dispatch in one file.

The target architecture preserves the two-path inference model (SDK for fast chat/tools, Cognitive OS for council deliberation) but makes the plugin a **thin, modular proxy** that defers model configuration authority to the backend. Success = the plugin has no hardcoded model presets, only one `fetch()` to Cognitive OS, and `chat-view.ts` is split into ≤6 files each under 300 lines.

## ⚠️ Difficulties & Constraints

1. **Technical**: The AI Providers SDK (`@obsidian-ai-providers/sdk`) is correctly used for the fast chat/tooling path and must **not** be dropped. The risk is accidentally breaking the streaming chat path by over-abstracting. The refactor keeps `aiProviders.execute()` calls inside each tool module — each tool is still a thin wrapper around a single SDK call.
2. **Technical**: `chat-view.ts` at ~2100 lines is large but well-structured internally — the split must preserve exact behaviour of the model selector, tool buttons, history navigation, and attachment handling. Acceptance criteria must be binary and testable.
3. **Operational**: Removing `model_presets` from `PromptRequest` / `orchestrator.process_request()` requires verifying no other caller (Telegram bot, dashboard, tests) passes that field. A grep of all callers is task 0.
4. **Aesthetic / Sovereign**: The plugin's chat UX (ribbon icon, model selector, tools panel) must remain identical post-refactor. Dark Maestro alignment: the user should not notice the change except faster startup (presets fetched, not hardcoded).

## 📋 Implementation Tasks (Beta Council will refine)

1. **T0 — Audit callers of `model_presets`**: Grep `cognitive-os/` + `obsidian-lmstudio-agent/` + dashboard `script.js` for `model_presets`. Confirm only `canvas-commands.ts` sends it and only `api.py`/`orchestrator.py` accept it. Document all callers.
2. **T1 — Extract `modelResolver.ts`**: Move `getProviderAndModel()` from both `chat-view.ts` and `editor-commands.ts` into a single module. Both callers import from `modelResolver`. Add `fetchPresetsFromBackend()` that calls `GET /api/config` and caches `model_presets`.
3. **T2 — Extract `cogOsCommands.ts` from `main.ts`**: Move all Cognitive OS canvas-node-menu handlers (lines 36-65), editor-menu handlers (lines 70-91), and related command registrations into a dedicated module. `main.ts` calls `registerCogOsCommands(this)`.
4. **T3 — Unify `canvas-commands.ts` under `cogOsService.ts`**: Replace the inline `fetch()` in `canvas-commands.ts:87-106` with a call to `sendToCognitiveOS()`. Remove the hardcoded `'http://127.0.0.1:5000/process'` fallback URL (line 95). Stop sending `model_presets` in the payload.
5. **T4 — Remove dead `model_presets` from backend**: Strip `model_presets` from `PromptRequest` (`api.py:976`), from `process_request()` signature (`orchestrator.py:210`), and from the `process_prompt` call site (`api.py:999`). Run `test_api_endpoints.py` to verify no regressions.
6. **T5 — Split `chat-view.ts` tools into `src/tools/*.ts`**: Extract `toolTemplates`, `toolAnalyzeVault`, `toolAutoTag`, `toolGenerateAISuggestions`, `toolDailyNote`, `toolGenerateImage`, `toolFindDuplicates`, and the summarize/help-prompt inline tools into individual modules. Each exports `async function execute(ctx: ToolContext): Promise<void>`. `chat-view.ts` delegates to them.
7. **T6 — Reduce `settings.ts` model slots**: Remove `toolAnalyzeVaultModel`, `toolSummarizeNoteModel`, `toolAISuggestionsModel`, `toolHelpPromptModel`, `toolTemplatesModel` from `AgentPluginSettings`. Tools use the active chat model from the model selector (which references a preset). Preserve `chatModel`, `editModel`, `embeddingModel` as the 3 core slots — but `chatModel` now stores a `preset::id` reference, not a raw `providerId::model` string.
8. **T7 — Plugin fetches presets from backend at startup**: `onload()` calls `fetchPresetsFromBackend()` to populate `settings.modelPresets` from `GET /api/config`. The hardcoded defaults in `DEFAULT_SETTINGS` become fallbacks (used only when the backend is unreachable). Settings UI shows presets sourced from backend.
9. **T8 — Verify all acceptance criteria**: Run the checklist below. Test: chat with model selector, each tool button, canvas node → Design Council, editor right-click → Auto-Route, file right-click → Oracle Council.

## 🚫 Veto Points (anything the Boardroom should reject)

- ❌ **Do NOT remove the `@obsidian-ai-providers/sdk` dependency.** The SDK is the correct tool for fast single-turn chat/tool inference. The proposal only refactors *how models are discovered and configured*, not *how inference is executed*.
- ❌ **Do NOT force chat messages through `/api/process`.** That would add 2-5 seconds of orchestration overhead to every chat message. The two-path architecture (SDK for chat, Cognitive OS for councils) is intentional and correct.
- ❌ **Do NOT merge tool modules back into `chat-view.ts` during implementation.** If a tool module grows past 300 lines, it should be split further — never folded back into the chat view.
- ❌ **Do NOT keep `model_presets` on `PromptRequest` "just in case."** The parameter has been dead code since it was added. Councils read model config from `master_config.md` via `get_role_config()`. The passthrough adds confusion without value.
