## 📥 Original Request

> **Origin**: Systems Architect — captured from user request:
> "I need an agent that logs this progress and puts it on the net :)"

The cognitive-os has produced extraordinary daily output (12 days from `git init` to a 5-phase governance stack with 35 binding gates and 155 tests) but **none of it is legible to anyone outside the workspace**. Recruiters, collaborators, the indie-hacker community, and future-you all benefit from a public audit trail. Manually writing a devlog is exactly the kind of work the system is supposed to automate.

This proposal builds a **DevLog Agent** that:

1. Reads the day's evidence (git commits, gate deltas, council verdicts, test counts)
2. Synthesises a short narrative via an existing council role
3. Routes the synthesis through OutputRouter (Phase 2) to a vault inbox + a publish queue
4. Requires explicit human approval before anything leaves the laptop

---

## 🎯 Goal

After this lands:

- Every dev-day produces a draft devlog post in `Z-Inbox/devlogs/YYYY-MM-DD.md` (vault) and `dev/devlogs/_pending/YYYY-MM-DD.md` (publish queue) **automatically** at a configurable cadence (default: 21:00 local, or on-demand via CLI).
- Each draft contains: commit summary, gate delta (e.g. `25/35 → 35/35`), test count delta, one human-readable highlight (the "story of the day"), and a markdown post optimised for dev.to / GitHub Pages.
- A separate `publish` command pushes approved drafts to one or more configured platforms (dev.to + GitHub Pages first; X/BlueSky later).
- The act of publishing is **logged through Phase 1's ApprovalLogger** so the public devlog has a verifiable chain-of-custody back to the actual git commits it describes.
- No autopost. Ever. Human approves; system publishes.

## ✅ Deliverables

### Core (Phase 1 of this proposal)

1. **`src/devlog_agent.py`** — the synthesiser
   - Public surface: `class DevLogAgent` with:
     - `gather(date: date) -> DevLogEvidence` — assembles git commits, gate JSON, council JSONs, test count from that date
     - `synthesise(evidence: DevLogEvidence) -> DevLogDraft` — calls a council role (recommend `creative` or a new `devlog_scribe`) via the existing orchestrator
     - `route(draft: DevLogDraft) -> RoutingDecision` — uses `OutputRouter` to land it in both the vault inbox and the publish queue (Phase 2 dependency)

2. **`src/models/devlog.py`** — Pydantic models
   - `DevLogEvidence`: commits, gate_before/after, council_summaries, test_delta, highlight_hints
   - `DevLogDraft`: title, body_markdown, tweet_thread (4 entries, ≤280 chars each), tags, evidence_hash, date

3. **`config/devlog_config.yaml`** — what to gather, what NOT to gather
   - allowed_sources: list of paths the agent may read
   - **forbidden_sources**: list of paths it MUST NOT read (e.g. `Z-Inbox/`, anything in `mock_vault/`, anything tagged `private`)
   - cadence: cron-like spec
   - council_role: which role synthesises
   - platforms: which publish targets are configured

4. **`src/devlog_publisher.py`** — the publish layer (separate from the agent for testability)
   - `class DevLogPublisher` with one method per platform:
     - `to_github_pages(draft, branch="gh-pages")` — commits the markdown to `/devlog/YYYY-MM-DD.md` on the configured branch
     - `to_devto(draft, api_token)` — POSTs to dev.to API
     - Future: `to_bluesky`, `to_mastodon`, `to_x`
   - **All publish methods are gated by explicit `--approved` flag passed from CLI**

5. **`scripts/devlog.py`** — the CLI
   - `python scripts/devlog.py draft [--date YYYY-MM-DD]` — generates today's (or specified date's) draft
   - `python scripts/devlog.py list-pending` — shows drafts awaiting approval
   - `python scripts/devlog.py approve <date>` — moves from `_pending/` to `_approved/`
   - `python scripts/devlog.py publish <date> --to github_pages,devto` — publishes approved draft

6. **Tests**
   - `tests/test_devlog_agent.py` — evidence-gathering produces expected shape; synthesise is mocked
   - `tests/test_devlog_publisher.py` — each publisher works against a mocked HTTP / git surface
   - `tests/test_devlog_cli.py` — CLI commands respect the approval boundary
   - Target: ≥12 test cases

### Stretch (Phase 2 of this proposal — separate commit)

7. **Auto-schedule via Windows Task Scheduler / cron** (optional, off by default)
8. **Inline GIF/screenshot rendering** from `dashboard/` if present
9. **Weekly digest** — a Saturday post summarising the week

## 🛡 Binding constraints (would-be vetoes anticipated)

**CSTR-DEVLOG-V1 — No autopost.** The publish layer NEVER fires automatically. A human MUST run `scripts/devlog.py publish <date> --approved` explicitly. Any agentic auto-publish would be a HIGH-severity governance failure.

**CSTR-DEVLOG-V2 — Forbidden sources are forbidden.** The `forbidden_sources` config is enforced at gather-time, not synthesise-time. The agent does not get to see, summarise, or even know about content in `Z-Inbox/` (personal/business), `mock_vault/`, or any file with frontmatter tag `private: true`.

**CSTR-DEVLOG-V3 — All publishes go through ApprovalLogger.** The act of `publish` writes a record to the Phase 1 approval log with the draft's `evidence_hash`, the human approver, and the timestamp. This means the public devlog has a verifiable provenance trail.

**CSTR-DEVLOG-V4 — Single-writer rule applies.** The devlog publisher writes to the vault (`Z-Inbox/devlogs/`) ONLY via Phase 2's OutputRouter → ProposalSync chain. No direct vault writes from `devlog_publisher.py`. (Per ARCH-2007E0A1 T1.)

**CSTR-DEVLOG-V5 — Use existing infrastructure.** No new dependencies beyond what's already installed:
- `httpx` for HTTP (if not already → use stdlib `urllib`)
- `ruamel.yaml` for config (already there)
- `pydantic` for models (already there)
- Council synthesis via existing orchestrator (already there)

### Risk
- **Privacy spillage.** The whole point of the forbidden_sources guard is to prevent the agent from accidentally posting the contents of `Z-Inbox/Obsidian Quill - Strategic Plan.md` (or worse) to the internet. The guard must be tested with adversarial fixtures.
- **API tokens in git.** The `devto_api_token` MUST live in env vars / `.env` (already gitignored), never in `devlog_config.yaml`.
- **dev.to rate limits.** The publisher should honour `Retry-After` headers and never retry-storm on failure.

## 🎨 Aesthetic direction

Devlog posts adopt the **Dark Maestro** style guide (`docs/style/AESTHETIC.md`) but **softened for public consumption**:

- Pass/fail glyphs (■/□/▷) are used but explained on first appearance in each post
- Box-drawing headers OK for code blocks, replaced with markdown `##` for prose sections
- "Build-in-public" tone: direct, technical, no marketing speak, no false modesty
- Stories are about the *interesting decisions* (e.g. "the boardroom said use ruamel.yaml, here's why"), not the routine work
- Errors and failures are highlighted, not hidden — the audience wants to see real engineering

### 🔴 NEW dependency: Phase 5 (49798A0E) — Production Wiring

The DevLog Agent's `route()` step calls `OutputRouter.route()` and `OutputRouter.apply()`. These classes exist on disk and pass tests, but **they are not wired into the running `/process` pipeline**. The current production `/process` endpoint uses them (confirmed in `api.py` L1000-1009), but other code paths that the DevLog Agent would trigger (council synthesis → routing → vault write) go through `orchestrator.py`, which has minimal OutputRouter integration (only `is_output_router_enabled` flag check at L132).

**Without Phase 5's wiring, the DevLog Agent's council-synthesis step has no path to route its output to the vault.** This was not visible on May 23 because Phase 5 didn't exist yet.

### 🔴 Blocker: No dedicated synthesis role exists

The original proposal suggested using `board_creative` (hermes-4.3-36b-heretic-i1) for synthesis. This is problematic:

| Issue | Detail |
|---|---|
| **Wrong prompt format** | `board_creative` has a system prompt that expects boardroom deliberation context and outputs JSON verdicts (`{"creative_vision": ..., "veto_points": [...]}`), not public-facing blog prose |
| **Wrong temperature** | `board_creative` runs at `temperature: 1` with high top_p — good for creative ideation, terrible for factual technical writing |
| **Wrong output contract** | The `DevLogDraft` model expects `title`, `body_markdown`, `tweet_thread`, `tags` — none of which `board_creative` knows how to produce |
| **Wrong model size** | 36B is oversized for what is essentially a summarization task with structured inputs; 8B-14B is more appropriate and has lower latency |

**Mandate: Create a new `devlog_scribe` role** in `master_config.md` *before* Beta Testing begins. This role:
- Uses a smaller, faster model (recommend: `qwen3.6-14b-heretic-uncensored` or `deepseek-coder-v2-lite-instruct`)
- Temperature 0.7, top_p 0.9 (factual, not creative)
- System prompt: "You are the DevLog Scribe for the Dark Maestro cognitive-os. You receive structured evidence (git commits, gate deltas, council verdicts, test counts) and produce a public-facing devlog post. Tone: direct, technical, build-in-public. Highlight interesting decisions, not routine work. Errors and failures are featured, not hidden. Output format: markdown with title, body, 4-tweet thread, and tags."
