## 📥 Original Request

> **Origin**: User request — "after all this architecture work I want to implement https://github.com/github/spec-kit"

The cognitive-os has built a full governance pipeline (5-phase proposal lifecycle, boardroom councils, handoff system, routing automation, workflow engine) but the **user-facing workflow** is still manual: file a proposal in Obsidian, wait for council verdict, work through a handoff with Cline. spec-kit provides a standardized front-end for Spec-Driven Development with slash commands (`/speckit.specify`, `/speckit.plan`, `/speckit.tasks`, `/speckit.implement`) that would make the cognitive-os accessible to any developer, not just its creator.

This proposal introduces spec-kit as the **presentation layer** of the cognitive-os, with the cognitive-os serving as the **execution engine** underneath.

---

## 🎯 Goal

After this lands:

- A developer types `/speckit.specify "Build a photo album app"` in VS Code → the cognitive-os files it as a DEV proposal, routes it through the boardroom, and generates a handoff with implementation tasks
- `/speckit.plan` maps to the Technical Meeting council (Phase 1)
- `/speckit.tasks` maps to the HandoffPlanner (`5DFB393F`) — not spec-kit's generic task generator
- `/speckit.implement` maps to the Beta/Alpha handoff → Cline execution pipeline
- The dashboard shows spec-kit-originated proposals alongside ARCH/DEV/NLST proposals
- An **Antigravity Preset** is published so any spec-kit user can install the cognitive-os governance workflow

## 🛡 Binding Constraints

**CSTR-SPECKIT-V1 — spec-kit is the UX, not the engine.** spec-kit never replaces the council system, the handoff pipeline, or the governance gates. It is a presentation layer that calls cognitive-os primitives. If spec-kit is uninstalled, the cognitive-os still works exactly as it does today (just via Obsidian + manual triggers instead of slash commands).

**CSTR-SPECKIT-V2 — No autopost tie-in.** spec-kit's `/speckit.implement` must NOT bypass the human approval gates. The DevLog Agent's publishing pipeline remains separate.

**CSTR-SPECKIT-V3 — Proposal provenance preserved.** All proposals originating from spec-kit must carry `origin: "spec-kit"` and flow through the same lifecycle as any other proposal. No spec-kit "fast lane" that skips council review.

**CSTR-SPECKIT-V4 — Gate compatibility.** spec-kit's `/speckit.analyze` must produce output compatible with `alpha_polish_check.py`. No competing gate systems.

## 🧠 Technical Assessment

### Complexity
**Low-Medium.** spec-kit is a Python CLI that installs slash commands as markdown prompt files. The cognitive-os already exposes all the primitives spec-kit needs. The work is mainly:
- Installing the CLI (trivial)
- Writing command files that call cognitive-os Python functions (moderate)
- Building the preset (moderate, but well-documented by spec-kit)

### Risks
| Risk | Mitigation |
|---|---|
| spec-kit commands bypass governance | CSTR-SPECKIT-V3: all proposals go through standard lifecycle |
| Two competing gate systems | CSTR-SPECKIT-V4: `/speckit.analyze` calls `alpha_polish_check.py` |
| spec-kit upgrade breaks integrations | Pin spec-kit version; preset is versioned independently |
| Community preset requires ongoing maintenance | Low burden — preset is mostly template overrides, not code |
