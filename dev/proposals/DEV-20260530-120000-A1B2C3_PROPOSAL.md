## Original Request

Implement dynamic context window sizing based on proposal token count to reduce memory usage and improve efficiency for smaller proposals. Deferred from ARCH-20260529-150000-C7EBA3E9 Alpha Polish Section C tasks (C1, C2, C3).

---

## Current State

- Infrastructure exists: `src/context_window_manager.py` with `get_effective_context_window()` function
- `PatternRequest` has `context_window_hint` field (optional int)
- All councils currently use fixed 32K context window regardless of proposal size

---

## Proposed Implementation

### 1. Token Measurement in API Layer

In `src/api.py`, before calling council in `_dispatch_proposal_council()` and `_run_beta_council_and_handoff()`:

```python
proposal_text = _read_proposal_text(proposal_id) or ""
approx_tokens = len(proposal_text) / 3.5  # Conservative estimate

# Round up to nearest 1K, minimum 8K
ctx_needed = max(8192, ((approx_tokens + 200 + 2000 + 1023) // 1024) * 1024)

# Pass to PatternRequest
req = PatternRequest(
    user_input=user_input,
    context_window_hint=ctx_needed
)
```

### 2. Apply Override in Council Runner

In `src/council_runner.py`, modify `run_council()`:

```python
for role_key, role_config in roles.items():
    effective_window = get_effective_context_window(
        base_window=role_config.get("context_window", 32768),
        context_window_hint=context_window_hint
    )
    logging.info(f"[COUNCIL] {role_key} context_window: {effective_window} (hint={context_window_hint})")
```

### 3. Verification

- **Small proposal** (C7EBA3E9, ~11.6KB, ~5.5K tokens) → should use 8K context
- **Large proposal** (DA5B0A2D, ~37.6KB, ~12.5K tokens) → should use 16K context
- Verify no `[TRUNCATED]` markers in council output

## 📎 ADDENDUM — May 30, 2026 Context Budget Realignment

**Trigger**: Boardroom chairman context bumped from 32k → 48k (May 30, 2026)
to accommodate system context injection (C7EBA3E9, ~8,000 chars / ~2,000 tokens)
plus 5 prior chairs' meeting history. The original proposal's clamp floor of
8,192 tokens is no longer safe.

### Revised Clamp Floor Calculation

The effective context window MUST satisfy:

```
ctx_floor = system_context_tokens    # ~2,000 (C7EBA3E9)
          + proposal_tokens           # varies per proposal
          + meeting_history_estimate  # 5 chairs × ~1,500 tok each = ~7,500
          + synthesis_max_tokens      # 16,384 (chairman, May 30 bump)
          + headroom                  # 2,000 safety margin
          ─────────────────────────
          = ~27,884 minimum
```

Round to nearest 1,024 → **floor: 28,672**.

| Proposal size | Rounded floor | Before (flat 8k) | After (28,672 base) |
|---|---|---|---|
| Small (~2K tok) | 28,672 | ❌ chairman suffocated | ✅ 12,328 headroom |
| Medium (~8K tok) | 34,816 | ❌ | ✅ 6,184 headroom |
| Large (~15K tok) | 43,008 | ❌ | ✅ all fits |
| Very large (~25K tok) | 48,384 → cap | ❌ | ⚠️ edges toward master_config cap |

### Consequence

The proposal's original "8K minimum" spec is **invalidated** by the C7EBA3E9
system context injection and the May 30 chairman token bump. The clamp floor
is now ~28K, not 8K. For the common case (proposals under 15K tokens), this
still saves ~20K vs the master_config defaults — a ~42% reduction, down from
the originally advertised 75%.

The `get_effective_context_window()` call in `council_runner.py` must compute
the floor from `context_window_hint + 26,500` (system_context + meeting_history +
max_tokens + headroom estimate), not from a hardcoded constant. This ensures
the formula stays correct as C7EBA3E9 context and chairman config evolve.
