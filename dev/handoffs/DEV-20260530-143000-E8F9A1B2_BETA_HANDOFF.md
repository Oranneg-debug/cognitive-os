## **📜 Executive Summary**
This engineering plan outlines the modular refactoring of the `obsidian-lmstudio-agent` plugin to eliminate redundancy, unify model settings with the backend's `master_config.md`, and consolidate HTTP logic. The goal is to transform a monolithic 2100-line `chat-view.ts` into a modular architecture with a single source of truth for model configurations, ensuring cleaner separation of concerns and improved maintainability.

---

## **🎯 Vision & Goals**
### **Core Vision**
The refactored plugin will act as a **thin, modular proxy** that delegates model configuration to the backend (`master_config.md`), consolidates HTTP logic, and splits the monolithic `chat-view.ts` into focused modules. This aligns with the **Dark Maestro’s Architectural Elegance**, ensuring the plugin remains lightweight while being more resilient and extensible.

### **Key Goals**
1. **Eliminate Redundancy**: Remove duplicated model presets and HTTP logic.
2. **Single Source of Truth**: Unify model settings with `master_config.md`.
3. **Modularity**: Split `chat-view.ts` into ≤6 focused modules (<300 lines each).
4. **Preserve Functionality**: Maintain identical UX, including model selector, tool buttons, and council routing.
5. **Performance**: Ensure no breaking changes to existing functionality.

---

## **🔧 Architecture Overview**
The refactored system consists of the following components:

| **Component**               | **Purpose**                                                                 | **Key Files**                          |
|-----------------------------|-----------------------------------------------------------------------------|----------------------------------------|
| **User Interfaces**         | Telegram Bot, Obsidian Plugin, Web Dashboard                              | `main.ts`, `settings.ts`               |
| **API & Classification Layer** | FastAPI Server, Sentry Router                                             | `cogOsService.ts`, `api.py`            |
| **Orchestration Layer**     | Orchestrator, Council Runner                                               | `orchestrator.py`                      |
| **Governance Foundation**   | Workflow Engine, Governance UoW                                             | `master_config.md`                     |
| **LLM Lifecycle Handling**  | LLM Client, LM Studio                                                       | `modelResolver.ts`                     |
| **Persistence Layers**      | Plugin settings, model presets, tool configurations                        | `settings.ts`, `tools/*.ts`           |

### **Data Flow**
1. **Plugin Load**: Fetches model presets from `GET /api/config` (backend).
2. **Model Resolution**: Uses `modelResolver.ts` to resolve provider/model pairs.
3. **Tool Execution**: Delegates tool execution to modular `src/tools/*.ts` modules.
4. **Cognitive OS Routing**: Uses `cogOsService.ts` for HTTP requests to `/api/process`.
5. **Backend**: Removes `model_presets` from `PromptRequest` and `process_request()`.
