# HandoffPlanner Output Specification

**Proposal:** ARCH-20260524-011510-5DFB393F (HandoffPlanner, deliverable A8)
**Status:** Stable (v1.0)
**Last updated:** 2026-05-25
**Authority:** This document is the single source of truth for the
shape of HandoffPlanner output. The Pydantic models in
`src/models/handoff_plan.py` and the renderer in
`HandoffPlan.to_markdown()` must agree with this spec. If they
disagree, this spec wins and the code is the bug.

---

## 1. Scope

The HandoffPlanner emits two artefacts per invocation:

| Artefact | Format | Contract |
|---|---|---|
| Structured plan | `HandoffPlan` Pydantic object | `src/models/handoff_plan.py` |
| Rendered markdown | UTF-8 string | This spec + `HandoffPlan.to_markdown()` |

Callers receive the structured plan; the rendered markdown is what
ends up inside a handoff document's `## 🔧 Implementation Tasks`
section.

This spec covers only the markdown rendering. The JSON intermediate
(what the LLM emits) follows the Pydantic schema — see
`_PLANNER_SYSTEM_PROMPT` in `src/handoff_planner.py` for the
LLM-facing description.

---

## 2. JSON intermediate (LLM → planner)

The LLM emits a single JSON object matching:

```json
{
  "proposal_id": "ARCH-… or DEV-…",
  "sections": [
    {
      "name": "<short section title>",
      "tasks": [
        {
          "id": "<one uppercase letter + digits, e.g. A1>",
          "title": "<single-line active title>",
          "subtasks": ["<step 1>", "<step 2>"],
          "acceptance": "<single-line acceptance criterion>",
          "constraints": ["CSTR-X-V2", "H3"],
          "file_paths": ["src/x.py", "tests/test_x.py"]
        }
      ]
    }
  ]
}
```

### Validation rules

| Field | Rule |
|---|---|
| `proposal_id` | min length 1; injected by the planner if omitted |
| `sections` | min length 1 |
| `sections[].name` | min length 1 |
| `sections[].tasks` | min length 1 |
| `tasks[].id` | matches `^[A-Z]\d+$` (e.g. `A1`, `B12`; not `a1`, `AA1`, `1A`) |
| `tasks[].title` | min length 1, no newlines |
| `tasks[].acceptance` | min length 1, no newlines |
| `tasks[].subtasks` | optional, list of strings |
| `tasks[].constraints` | optional, list of strings |
| `tasks[].file_paths` | optional, list of strings (repo-relative) |
| Cross-task | `tasks[].id` must be unique across the entire plan |

Any deviation is a `ValidationError`. The planner retries once with
the error injected into the prompt; on second failure it dead-letters
and raises `PlannerValidationFailed`.

## 3. Markdown rendering (`HandoffPlan.to_markdown`)

Returns a string suitable as the body of the `## 🔧 Implementation Tasks`
section. **The caller is responsible for emitting the parent `##`
header** — `to_markdown()` returns only the body.

### 3.1 Section header

```markdown
### Section <LETTER> — <section.name>
```

- `<LETTER>` is the section's alphabetical position: `A`, `B`, …, `Z`,
  then `AA`, `AB`, … This is computed from the section's index in
  `HandoffPlan.sections` and is **independent of `section.name`** —
  the name is the human label, the letter is the deterministic
  identifier.
- Separator is an em-dash (` — `), not a hyphen.

### 3.2 Task

Each task renders as:

```markdown
- [ ] **[✏️ PLANNER] <id>. <title>**
   - [ ] <subtask 1>
   - [ ] <subtask 2>
   - **Acceptance:** <acceptance>
   - **Constraints:** <c1>, <c2>
   - **Files:** `<file1>`, `<file2>`
```

Rules:

- **Visual prefix `[✏️ PLANNER]` (CREATIVE-A2)** appears in every task
  title verbatim. The exact byte sequence is the module constant
  `PLANNER_TASK_PREFIX` in `src/models/handoff_plan.py`.
- **Title format** is `<id>. <title>` (with the dot and space).
- **Subtasks** are 3-space indented (`   - [ ] <text>`). Unticked.
- **Acceptance** is single-line, prefixed `   - **Acceptance:** `.
- **Constraints** are joined with `, ` (comma + space). Omitted entirely
  if the list is empty.
- **Files** are each wrapped in backticks and joined with `, `. Omitted
  entirely if the list is empty.
- Each task is preceded by **one blank line** (separation from prior
  task).

### 3.3 Signature footer (CREATIVE-A4)

The rendered output ends with:

```

---
*Generated by HandoffPlanner v1.0. Dark Maestro Ready.*
```

Exactly: a blank line, three hyphens, a blank line, the italicised
single-line signature, and a trailing newline. The exact byte sequence
is the module constant `PLANNER_SIGNATURE` in
`src/models/handoff_plan.py`.

## 4. Worked examples

### 4.1 Minimal — one section, two tasks

Input plan:

```json
{
  "proposal_id": "ARCH-EXAMPLE-001",
  "sections": [
    {
      "name": "Core",
      "tasks": [
        {
          "id": "A1",
          "title": "Wire OutputRouter into /process",
          "subtasks": ["import at module top", "instantiate at startup"],
          "acceptance": "POST /process persists synthesis via OutputRouter.apply()",
          "constraints": ["H3"],
          "file_paths": ["src/api.py"]
        },
        {
          "id": "A2",
          "title": "Cover the wiring with a test",
          "subtasks": [],
          "acceptance": "tests/integration/test_api_process_uses_output_router.py passes",
          "constraints": ["H3", "CSTR-PLANNER-V4"],
          "file_paths": ["tests/integration/test_api_process_uses_output_router.py"]
        }
      ]
    }
  ]
}
```

Rendered output:

```markdown
### Section A — Core

- [ ] **[✏️ PLANNER] A1. Wire OutputRouter into /process**
   - [ ] import at module top
   - [ ] instantiate at startup
   - **Acceptance:** POST /process persists synthesis via OutputRouter.apply()
   - **Constraints:** H3
   - **Files:** `src/api.py`

- [ ] **[✏️ PLANNER] A2. Cover the wiring with a test**
   - **Acceptance:** tests/integration/test_api_process_uses_output_router.py passes
   - **Constraints:** H3, CSTR-PLANNER-V4
   - **Files:** `tests/integration/test_api_process_uses_output_router.py`

---
*Generated by HandoffPlanner v1.0. Dark Maestro Ready.*
```

## 5. Fallback notice (CSTR-PLANNER-V2)

When the planner is invoked but fails (timeout, validation failure
after retry, import error, or any other exception), `handoff_writer`
falls back to the legacy regex extractor and prepends this exact
notice as the FIRST line of the tasks block:

```
> ⚠️ PLANNER FAILED, FALLBACK ACTIVE: <short reason>. Tasks extracted via legacy regex.
```

The exact template lives at `_PLANNER_FALLBACK_NOTICE_TEMPLATE` in
`src/handoff_writer.py`. Reasons are short, human-readable strings —
not stack traces. The full stack trace is in the logger output and,
for validation failures, in the dead-letter file at
`dev/failed_routings/handoff_planner_<ts>.failed.md`.

When the planner is **disabled** via `handoff.planner_enabled: false`
in `master_config.md`, no notice is prepended — the legacy block is
the desired output in that case.

## 6. Model choice + swap criteria

**Default model:** `ministral-3-3b-instruct-2512` (already loaded as
moderator/scribe — no new VRAM allocation).

**Sampling:**

- `temperature: 0.3` (determinism over creativity)
- `top_p: 0.9`, `top_k: 40`, `min_p: 0.1`
- `max_tokens: 8192` (enough for ~30–50 detailed checklist items)

**Hard timeout:** 60 seconds per call (Specialist amendment A2).

### Swap trigger

If, over 20 consecutive planner invocations:

- validation success rate falls below **90%**, OR
- fallback rate exceeds **5%** due to malformed LLM output (NOT timeouts;
  those usually indicate VRAM contention, not model capability)

…then swap to **`qwen3-vl-4b-thinking`** (also already loaded, 4B
parameters, similarly fast). The swap is a one-line edit in
`dev/master_config.md`:

```yaml
roles:
  handoff_planner:
    model: qwen3-vl-4b-thinking
```

No code change required. The system prompt remains valid for the new
model — the constraints are structural, not vocabulary.

Telemetry source: logger output of `src.handoff_planner` plus the
dead-letter file count in `dev/failed_routings/handoff_planner_*.failed.md`.

## 7. Compliance check

A renderer change is considered compliant with this spec iff:

1. The Pydantic schema in `src/models/handoff_plan.py` enforces all
   validation rules in §2.
2. `HandoffPlan.to_markdown()` produces output that matches §3 byte-
   for-byte for every valid input plan.
3. The two worked examples in §4 round-trip: rendering them and
   parsing the result back (via a structural-equivalence helper)
   yields plans that compare equal modulo `generated_at`.
4. The fallback notice exactly matches §5.
5. The default role config in `dev/master_config.md` matches §6.

Tests in `tests/test_handoff_planner.py` (deliverable A9) enforce
items 1–3. Item 4 is enforced by integration tests in
`tests/integration/test_beta_handoff_uses_planner.py` (deliverable
A10). Item 5 is checked by the boot-time validator in `src/api.py`
(via `get_role_config('handoff_planner')`).
